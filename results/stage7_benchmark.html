Why GPU is slower here Every result above was independently re-verified against the CPU reference (point_equal) before being trusted — the GPU implementation is correct at every size tested. It is also currently slower than CPU, and the gap widens with n rather than closing. The reason is structural: Stage 6’s bucket-fill shader runs exactly 2window_bits = 256 threads per dispatch (one per bucket, chosen to avoid races without atomics — there’s no atomic elliptic-curve-point-addition primitive to begin with). Each thread scans all n points sequentially, so a dispatch takes O(n) time on a GPU that can run far more than 256 threads at once. At n = 218 a single dispatch exceeded Windows’ ~2s TDR timeout and the driver killed it (VK_ERROR_DEVICE_LOST) — which is why this chart stops at 216. Reaching the original 220 target needs a bucket-assignment scheme with far more active threads (e.g. one thread per point instead of per bucket); that’s real algorithm work, left for Stage 8.

What the sweep found Stage 7 flagged the GPU implementation as underused — only 2window_bits threads run per dispatch, one per bucket. This sweep holds n fixed and varies window_bits to test that directly, and the result confirms it sharply: GPU time drops from 58.2 s at window_bits=2 (just 4 threads active) to 1.5 s at window_bits=10 (1,024 threads) — a ~37× improvement from one parameter. Past that point it gets worse again (2.4 s at window_bits=12): more buckets means more per-window bookkeeping — a larger bucket array to zero and reduce — and that overhead starts to dominate once thread count stops being the bottleneck. window_bits=10 is the sweet spot for this n, where GPU closes to within ~2× of CPU instead of ~20× behind. It still doesn’t beat CPU outright at any window size tried — getting there needs the higher-parallelism bucket redesign noted above, not just retuning this knob.
